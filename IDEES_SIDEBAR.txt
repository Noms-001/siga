SITUATION ACTUELLE
-----------------
Le schema definit 38 tables. Les sidebars referencent deja ~20 routes, mais le
router n'en declare que 4 reelles :

  - /dashboard, /profile                (frontoffice)
  - /backoffice/dashboard               (backoffice)
  - /login, /forgot-password, /reset-password

Toutes les autres entrees de menu actuelles sont donc des liens morts. Les
propositions ci-dessous servent a la fois de cible de developpement et de
structure de menu.

La logique retenue : regrouper par METIER (ce que l'utilisateur manipule),
jamais par table. Une table ne devient une entree de menu que si l'utilisateur
ecrit ou lit des donnees directement.

================================================================================
  4. TABLES SANS ENTREE DEDIEE - A TRAITER COMME DES ONGLETS
================================================================================

Plutot que de creer des pages inutiles, ces tables se consultent a l'interieur
d'une page mere, via des onglets. C'est le choix le plus econome en ecrans.

  sous_activite, resultat_intermediaire
      -> onglets de la fiche Activite
  activite_indicateur
      -> onglet "Indicateurs" de la fiche Activite
  affectation_sous_activite
      -> onglet "Affectations" de la fiche Activite
  affectation_plan_action
      -> onglet "Affectations" de la fiche Plan d'action
  plan_action_origine / origine
      -> onglet "Origines" de la fiche Plan d'action
  type_activite_service
      -> onglet "Services admis" de la fiche Type d'activite
  historique_activite
      -> panneau "Historique" (drawer) sur la fiche Activite


================================================================================
  5. PERMISSIONS : NOMMER LES ENTITES POUR LE MENU
================================================================================

La table permission a (ressource, action) et se rattache a un poste via
poste_permission. Le menu peut etre pilote par ces droits plutot que par le
role. Convention proposee, alignee sur la table permission :

  ressource                actions possibles
  ------------------------  ------------------------------------------
  activite                 lire, creer, modifier, supprimer, valider
  sous_activite            lire, creer, modifier
  procedure                lire, creer, modifier, valider
  livrable                 lire, deposer, supprimer
  plan_action              lire, creer, modifier, valider
  indicateur               lire, creer, modifier
  valeur_indicateur        lire, saisir
  notification             lire
  departement / service    lire, creer, modifier
  site / priorite / statut lire, creer, modifier
  type_activite            lire, creer, modifier
  objectif_specifique      lire, creer, modifier
  utilisateur              lire, creer, modifier, desactiver
  poste                    lire, creer, modifier
  role                     lire, creer, modifier
  permission               lire, creer
  parametre                lire, modifier

  Exemple de code dans le sidebar :

      { label: 'Activites', to: '/activites', icon: 'bi bi-list-task',
        permission: 'activite:lire' }

  Une entree sans la permission correspondante n'est pas rendue. C'est plus
  robuste qu'un `if (role === 'ADMIN')` code en dur dans le template, et cela
  evite d'avoir a retoucher le sidebar a chaque nouveau role.

  ATTENTION : le backend n'expose aujourd'hui que `postes` (liste de libelles)
  dans LoginResponse et ProfileResponse. Il n'expose pas encore les codes de
  permission. Ce mecanisme suppose donc une evolution de l'API.


================================================================================
  6. DETAIL D'ERGONOMIE
================================================================================

ORDRE DES SECTIONS
  La frequence d'usage decroissante doit guider l'ordre. Regle simple :
  une section utilisee tous les jours reste au-dessus de la ligne de flottaison,
  une section d'administration passe sous un separateur, en bas.

  Le menu actuel suit deja correctement cette regle (Pilotage, Activites,
  Plan d'action, Indicateurs, puis Utilisateurs/Notifications, puis Profil).

COMPTEUR DE NOTIFICATIONS
  Le badge existant sur Notifications peut afficher un vrai compteur, alimenté
  par notification.date_lecture IS NULL pour l'utilisateur connecte. La table
  notification(id_priorite, id_utilisateur, date_lecture) le permet
  directement, sans agregation complexe.

RECHERCHE
  Le champ recherche de la navbar est aujourd'hui decoratif. Il pourrait
  indexer au minimum activite.designation, procedure.designation,
  plan_action.designation et utilisateur.nom/prenom. Les quatre tables
  portent une colonne designation ou nom, donc le prefixe est un LIKE simple.

ETAT VIDE
  Chaque page listant une table (service, site, priorite, statut) aura un etat
  vide. Prevoir une variante de carte qui explique l'action attendue
  ("Aucun site enregistre. Ajouter un site") plutot qu'un simple tableau vide.

LIBELLE DES MENUS
  Pluriel pour les listes d'entites, singulier pour les formulaires de saisie.
  Le menu actuel melange les deux ("Nouvelle activite" est au pluriel dans son
  libelle, "Liste des activites" est correct). Uniformiser :
  "Nouvelle activite", "Nouvelle procedure", "Nouveau plan".

================================================================================
  8. POINT D'ATTENTION
================================================================================

Le menu actuel du frontoffice ne contient aucune entree pour les LIVRABLES ni
pour les FICHIERS, alors que le schema les prevoit (livrable_sous_activite,
fichier_sous_activite) et qu'ils sont le livrable central d'une activite. Si le
document de depot n'est pas accessible, l'utilisateur n'a aucun moyen de
remonter son travail.

A l'inverse, le menu actuel ne prevoit pas d'espace de saisie pour les
INDICATEURS, alors que le schema prevoit valeur_indicateur avec une periode et
un utilisateur contributeur. Sans ecran de saisie, la table reste vide et le
tableau de bord de pilotage n'a rien a afficher.

Ces deux manques sont les plus structurants du menu actuel.
